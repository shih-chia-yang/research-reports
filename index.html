6. 實驗方法與可信範圍

六個任務涵蓋單元、功能、整合各兩個；每個 task／arm 進行三次獨立生成，使用相同模型識別字 gpt-6.1-sol、固定共用輸入與唯讀隔離 session。A／B／C 的指示處理如主文所列。Graph 與 Markdown 是不同批次；本報告固定讀取其 schedule 中的 54 筆，不把資料夾內額外 probe／retry 當成正式樣本。

兩位盲評者各對 54 份案例的十個項目給 0／1／2 分。Primary 是前九項平均，Economy 第十項單獨報告；先取同一產出的兩位平均，再算 arm 平均。BDD pass 依兩評平均：BDD adequacy＝2，Given／When／Then 均至少 1。這些門檻不證明測試可編譯或可執行。

配對比較使用 18 個 task × replicate blocks，20,000 次 bootstrap，seed=20261026；block 內保留 A／B／C 配對，不把 108 份 review 當成 108 個獨立生成樣本。固定任務集的差異、三次重複與探索性分析都限制外推。區間是百分位法：排序後第 500 與第 19,500 個重抽樣平均值。

Reviewer 逐項完全一致率 93.3%，線性加權一致度 96.7%。這是評分一致性，並非對測試正確性的外部驗證；Then 的完全一致率只有 79.6%，個別判斷仍有不確定性。

實驗輸入 Graph 為固定快照：104 vertices／99 edges，coverage=partial、dependencies=not_inferred、semantic_equivalence=not_proven。此處使用的是當時快照，未以後來的 Semantic Graph 工具改動重寫實驗。未進行 C# 測試實作或缺陷植入；clarification_rate 有缺值且混有 reviewer 預測，不能當成實際追問率。未觀察到 contract hallucination 也不能當成已獨立驗證沒有幻覺。

7. 後續實驗：定位規則，而不是只選總分最高者

先對 B 的六個規則區塊逐一移除，再測重要的兩兩交互作用；使用固定輸入、同 block 隨機順序、獨立 session 與盲評。除了 Primary，同時追蹤完整性、資料分離、成本與缺漏。完整 suite 與逐案例是不同實驗單位，應另建批次；目前 dry run 不能當成正式消融結論。

確認有效規則後，再將案例實作為測試，量測是否能偵測事先定義的缺陷。若要主張 Markdown／Graph 等效，需事先訂定實務等效範圍並設計相對應實驗。

# 測試文件寫作

讓讀者不必查閱受測程式，就能理解測試條件、操作與預期結果。

## 使用方式

- 處理測試計畫時，閱讀[計畫欄位](references/plan-fields.md)。
- 處理案例、命名或測試註解時，閱讀[案例寫法](references/case-writing.md)。

## 核心原則

- 依需求與公開契約建立預期結果，不從受測程式反推。
- 具體寫出對象、條件、操作與結果，避免「適用列」「推進」「符合預期」等模糊說法。
- 技術值須附語意說明，不能只寫 error/none 等代碼。
- 每個情境只有一個主要操作，預期值須有獨立來源。
- 保留既有案例識別碼與追溯關係，不因文字改寫擴張契約。
- 區分案例已設計、測試已實作及測試已執行。
- 沿用專案治理流程；只要求審查時，交付具體缺口，不直接改寫受審文件。

## 交付

核對實際差異、來源與連結，說明修改範圍、檢查結果及未驗證事項，排除過程產物與其他既有工作。

# 測試案例與程式寫法

案例必須足以實作，且不必查閱受測程式才能理解。可引用具體契約或共用資料；引用應能找到所需值與規則，不以資料代號取代情境。

## 核心內容

| 項目 | 內容 | 刪除後的問題 |
| --- | --- | --- |
| Intent | 本案驗證的規則或要辨識的缺陷 | 可能只照抄現有輸出，卻不知道測試為何存在 |
| Rule | 對應的契約條款或成員 | 無法查核預期結果是否成立 |
| Boundary | 引用計畫中的邊界；有差異時明列 | 無法決定真實依賴與替身的配置 |
| Given | 既有狀態、關鍵輸入與必要關係 | 無法準備足以觸發指定規則的資料 |
| When | 受測入口與一次主要操作 | 無法確定實際執行哪個行為 |
| Then | 預期值、可觀察變化與禁止副作用 | 無法寫出有效斷言或辨識錯誤原因 |

Rule 與 Boundary 可使用註解或案例文件連結，不要求重貼契約及計畫。Intent 可由清楚的案例名稱表達，不為欄位完整而重複同一句話。

保留專案既有 CaseId；它用於追溯，不代替情境說明。

## 刪除重複欄位

- 不另設 input：關鍵輸入放在 Given。
- 不另設 expected：預期值放在 Then。
- 不另設 level：由引用的 Boundary 取得分類。
- 不另存 test_class、test_method：以程式宣告為準。
- 不強制每案建立 fixture、cleanup 欄位：有資源或隔離需求時，在 Arrange、釋放區塊或共用 fixture 說明。
- 不另外撰寫與 Intent 相同的目的段落。

## 檔名與方法命名

沿用專案既有慣例。沒有既定慣例時：

- 檔名：<受測對象>Tests.cs。
- 類別：與檔名一致。
- 方法：<操作>_<關鍵條件>_<預期行為>，使用 PascalCase。
- 非同步測試回傳 Task，不使用 async void。

例如：

```text
RoutingTests.cs
  SpecMetadataPath_ValidScope_ReturnsDefaultMetadataPath

SubmitDocumentTests.cs
  Submit_RequiredSpecIsDraft_RejectsWithoutChanges
```

不強制將 CaseId 放進方法名稱；需要時使用測試框架標記。

## Given／When／Then 與 AAA

方法前描述情境，方法內說明目的並安排程式。以下為需要 C# 範例或測試實作時的格式，不要求純案例文件建立未執行的測試程式。

```csharp
/// Given：儲存庫根目錄為 [本機路徑已省略]，適用範圍為 sample。
/// When：取得 sample 規格文件的預設中繼資料路徑。
/// Then：回傳 [本機路徑已省略]。
[Fact]
public void SpecMetadataPath_ValidScope_ReturnsDefaultMetadataPath()
{
    // Intent：驗證預設目錄與檔名符合路徑契約。
    // Rule：Routing.SpecMetadataPath 的公開契約。
    // Boundary：計畫中的 Routing 純路徑計算邊界。

    // Arrange
    const string root = "[本機路徑已省略]";
    const string scope = "sample";
    const string expected =
        "[本機路徑已省略]

    // Act
    string actual = Routing.SpecMetadataPath(root, scope);

    // Assert
    Assert.Equal(expected, actual);
}
```

範例採 Linux 路徑。實際專案的 Rule、Boundary 應指向可定位的文件或成員。Given／When／Then 是情境註解慣例，不是 C# 內建的專用 XML 標籤。

## 情境要求

Given 寫出會影響判定的條件，不以「合法資料」「適用列」省略。

When 指定操作與對象，不以「推進」「處理」代替。

Then 說明結果與原因。技術值須附語意。例如，某 CLI 的公開契約使用 status 與 result.effects 時：

> 命令回報失敗（status=error），且未留下本次檔案變更（result.effects=none）。

未留下變更不代表從未寫入；若曾寫入後完全復原，仍須檢查逐檔寫入與復原紀錄。欄位名稱、值與語意以受測系統的公開契約為準。

預期值依公開契約獨立提供，不呼叫受測方法產生 expected。

負向案例通常只破壞一項條件，其餘條件保持合法，避免因其他原因失敗卻誤判通過。只有測規則優先序時，才刻意同時安排多項拒絕條件。

每次主要操作可有多項斷言。資料變體各自執行一次，不在同一情境串接多次業務操作。

## 最後核對

逐案回答：

1. 能否直接準備 Given 所需的資料？
2. 能否明確寫出一次 Act？
3. 能否由 Then 寫出斷言，並辨識指定的失敗原因？
4. 真實依賴與替身是否符合引用的 Boundary？
5. 刪掉任何補充文字後，是否仍保有同樣的判定能力？

前三項無法回答時，案例尚不足以實作。

# 測試計畫欄位

測試計畫保存各案例共用的契約、邊界與執行條件。案例只記錄差異，不重複整份計畫。以下項目可沿用既有章節與附件，不要求另建資料格式或逐字使用欄位名稱。

## 核心欄位

| 欄位 | 內容 | 刪除後的問題 |
| --- | --- | --- |
| target | 受測專案或模組 | 無法確認計畫適用哪個系統 |
| contracts | 契約位置及採用版本 | 無法判定預期行為依據哪份規格 |
| boundaries | 各測試群組的受測範圍與依賴配置 | 可能以替身取代受測行為，或將局部測試當成完整整合 |
| execution | 測試專案、執行環境、前置與命令 | 無法建立所需環境或重現執行 |

## contracts 的內容

| 屬性 | 內容 | 刪除後的問題 |
| --- | --- | --- |
| ref | 契約檔案或公開規格的位置 | 無法查核判準 |
| revision | 版本、commit 或內容摘要，依專案規則選用 | 契約更新後，無法確認案例採用的內容 |

不重複填入多種版本標記；使用足以定位採用內容的一種即可。

## boundaries 的內容

每個邊界以可供案例引用的名稱識別。

| 屬性 | 內容 | 刪除後的問題 |
| --- | --- | --- |
| name | 邊界名稱 | 案例無法明確引用共用配置 |
| subject | 受測入口及本群組驗證的行為 | 無法決定測試應從哪裡呼叫、驗證到哪裡 |
| real_dependencies | 必須使用的真實依賴；沒有時填無 | 無法確認哪些互動支撐測試結論 |
| substitutes | 可以替換的依賴及替換用途；沒有時填無 | 測試實作者可能自行替換核心行為 |
| exclusions | 容易被誤認為已驗證的範圍；沒有時填無 | 可能將局部結果解讀為更大的能力已通過 |

Unit、Functional、Integration 可作為群組分類，但分類名稱不能代替上述邊界。

## execution 的內容

| 屬性 | 內容 | 刪除後的問題 |
| --- | --- | --- |
| project | 測試專案路徑 | 無法確定測試放置與執行位置 |
| environment | 會影響執行的 OS、SDK、執行階段及外部依賴 | 可能在不具備必要條件的環境執行 |
| prerequisites | 命令執行前需要完成的準備；沒有時填無 | 可能將環境未準備完成誤判為產品缺陷 |
| command | 工作目錄及執行命令 | 無法重現計畫所定義的測試入口 |

版本與設定優先引用專案設定檔；只另外寫出其中無法取得的必要條件。

## 不列為核心的資料

下列資料依專案治理規則保存，不另設第二份：

- 文件識別碼、版本、負責人及核准狀態：沿用 metadata。
- 案例數量與需求對照：由案例索引整理。
- 測試資料與預期值：放在案例；確實共用時才抽成具名資料附件。
- 通過條件：由各案例的 Then 定義，不再另寫籠統的「全部正確」。
- 執行時間、通過數及證據：放在執行紀錄。

# B 組：稀疏測試案例表達規則

本提示詞只規範測試案例的表達方式，不重複共用提示詞中的資料來源、
契約權威性、輸出限制與案例識別碼規則。

## 案例註解

使用一般程式碼註解描述案例：

// <案例識別碼>｜<業務情境名稱>
// 規則：<要驗證的業務規則>
// 測試範圍：<本案例負責驗證的範圍與排除事項>
// 契約來源：<契約或規格來源>
// Given：<業務上的起始情境>
// When：<業務上的主要操作>
// Then：<業務上可觀測的結果>
// <補充限制或禁止誤判>

Given、When、Then 必須使用業務語言。

不要使用 XML 文件註解，例如：

/// <summary>
/// <remarks>

不要把下列技術細節放入 Given、When、Then：

- 內部狀態名稱；
- 技術回應結構；
- payload 欄位；
- 驗證結構；
- 事件或命令類別名稱；
- 假物件的具體欄位值；
- 預期狀態、事件與原因代碼。

## 測試資料

將下列內容放在 TestData、MemberData 或其他既有測試資料結構：

- fake object；
- 具體輸入值；
- 測試變體；
- 回應內容；
- 觀測結果；
- 預期狀態與事件；
- 禁止的副作用；
- 原因代碼；
- 其他可直接供測試程式使用的參數。

測試資料必須由固定資料或資料工廠提供。
不要在測試方法內臨時捏造案例值。

## 測試方法型態

依測試資料型態選擇測試方法：

- 單一固定情境使用 `[Fact]`；
- 多個參數化變體使用 `[Theory]` 與 `[MemberData]`；
- 不要在同一個測試方法上同時使用 `[Fact]` 與 `[Theory]`；
- 若使用既有的 `intent`、`#3A` 或其他測試本體骨架，保留原有名稱與位置；
- 不要自行新增與案例判定無關的說明性程式碼。

## 稀疏性

只保留實作與判定此案例所需的內容：

- 一個業務規則；
- 一個主要操作；
- 必要的預期結果；
- 必要的禁止副作用；
- 必要的測試資料引用。

不要重複規格文件、重述任務，或描述不屬於公開行為的實作細節。

負向案例只改變一個刻意破壞的條件，
除非任務明確要求測試條件優先順序。
