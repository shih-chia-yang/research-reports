各組使用相同的個人需求與設計資料；原始 L1～L4 文件、衍生 graph 與需求案例內容不公開。

組別提供的撰寫指示（摘要）與資料分離的直接關係

6. 如何計分，結果能說明到哪裡？

六個固定任務涵蓋單元、功能、整合各兩個。每組每任務各生成三份案例，合計 54 份；模型識別字均為 gpt-6.1-sol，工作階段彼此獨立，共用輸入相同。每份案例由兩位盲評者依十項標準評為 0、1、2 分，再取兩評平均；總分採前九項平均，第十項「精簡程度」另列。

BDD 是以 Given（起始條件）、When（操作）、Then（預期結果）描述行為的方式。本報告的 BDD pass 指「BDD 表達」兩評平均為 2，且 Given、When、Then 都至少 1 分。A 與 C 各 17/18 份達標，B 為 18/18；每組僅差一份，不足以推定穩定的通過率差異。

差值以相同任務、相同重複次序配對，共 18 對；以配對重抽樣（bootstrap）估計 95% 信賴區間（CI）。區間跨過零，表示這個估計仍容許兩組差異為零。區間未作多重比較校正，且只涵蓋六個固定任務的重複生成，不代表對所有需求都成立。兩位評分者逐項完全一致率為 93.3%，一致仍不等於外部正確性驗證。

這次量測的是案例文件品質。尚未將案例實作為 C# 測試，未驗證可編譯、可執行或缺陷偵測能力；實際實作者的追問率也未量測。A 與 B 同時改變內容、篇幅及表達方式，需後續實驗才能分辨各因素的作用。

7. 後續實驗：定位規則，而不是只選總分最高者

先對 B 的六個規則區塊逐一移除，再測重要的兩兩交互作用；使用固定輸入、同 block 隨機順序、獨立 session 與盲評。除了 Primary，同時追蹤完整性、資料分離、成本與缺漏。完整 suite 與逐案例是不同實驗單位，應另建批次；目前 dry run 不能當成正式消融結論。

確認有效規則後，再將案例實作為測試，量測是否能偵測事先定義的缺陷。若要主張 Markdown／Graph 等效，需事先訂定實務等效範圍並設計相對應實驗。
